GitHub Pages para tu CV estático

GitHub Pages es un servicio gratuito que publica sitios web estáticos directamente desde un repositorio de GitHub. Para un currículum o un portfolio es la opción perfecta: no necesitas servidor, ni pagar hosting, ni mantener nada. Subes tu HTML, CSS y JavaScript, y GitHub se encarga de servirlo con HTTPS, dominio propio y una red de distribución (CDN) rápida en todo el mundo.

Combinado con un diseño estático optimizado a mano, el resultado son páginas que cargan al instante y que puntúan al máximo en SEO y rendimiento, sin el peso de un framework.

¿Por qué estático en GitHub Pages?

  • Gratis y sin servidor: nada de VPS, Docker ni mantenimiento. Cero coste.
  • Sin autohosting: no dependes de tu luz ni de tu conexión; lo sirve la infraestructura de GitHub.
  • HTTPS y dominio propio: certificado automático y soporte para tu dominio personalizado mediante un fichero CNAME.
  • Despliegue con git push: cada cambio que subes se publica solo.
  • Rendimiento inmejorable: al ser archivos estáticos servidos por una CDN, la carga es casi instantánea.

Cómo publicarlo paso a paso

El proceso es muy sencillo. Para un sitio de usuario, el repositorio debe llamarse tu-usuario.github.io:

  1. Crea un repositorio público con el nombre tu-usuario.github.io.
  2. Sube tu web estática (al menos un index.html) a la rama main.
  3. En Settings → Pages, elige la rama main como origen.
  4. En un par de minutos tu web estará en https://tu-usuario.github.io.
  5. ¿Dominio propio? Añade un fichero CNAME con tu dominio y crea el registro DNS correspondiente.
Ejemplo: subir tu web y publicarla 
# Clona tu repo y entra en él
git clone https://github.com/tu-usuario/tu-usuario.github.io.git
cd tu-usuario.github.io

# Añade tu web estática (index.html, css/, js/, images/)
# Para un dominio propio (opcional):
echo "www.tudominio.com" > CNAME

git add .
git commit -m "Mi CV web estático"
git push origin main
# Listo: GitHub Pages lo publica automáticamente

Dominio propio y HTTPS

Si quieres que tu CV se vea en www.tudominio.com en lugar de usuario.github.io, solo tienes que apuntar tu dominio a GitHub Pages:

DNS para dominio personalizado (ejemplo) 
# Un subdominio (www) con un registro CNAME:
www    CNAME    tu-usuario.github.io

# O el dominio raíz con registros A a las IPs de GitHub Pages:
@      A        185.199.108.153
@      A        185.199.109.153
@      A        185.199.110.153
@      A        185.199.111.153

Después, en Settings → Pages, escribe tu dominio en Custom domain y activa Enforce HTTPS. GitHub emite el certificado automáticamente.

Alta disponibilidad con GitHub Pages

Un sitio estático no tiene por qué depender de un solo origen. Puedes montar un esquema de alta disponibilidad (HA) combinando tu propio servidor con GitHub Pages como respaldo automático, de forma que la web siempre esté en línea:

  • Origen principal: tu servidor (por ejemplo, detrás de un proxy inverso como Traefik) sirve la web con su propio certificado.
  • Respaldo: el mismo sitio, publicado en GitHub Pages, listo en otra infraestructura totalmente independiente.
  • Conmutación automática: un pequeño vigilante comprueba cada minuto si tu servidor responde; si se cae, cambia por API el registro DNS para que www apunte a GitHub Pages, y lo revierte cuando tu servidor vuelve.
  • Despliegue único: con un git push actualizas los dos orígenes, así que nunca quedan desincronizados.

El resultado: si falla tu luz, tu conexión o tu servidor, la web sigue sirviéndose desde GitHub Pages sin que nadie lo note. Lo mejor de ambos mundos: control propio cuando todo va bien, y la red global de GitHub como red de seguridad gratuita.

La gran limitación (y por qué la culpa es de Google)

GitHub Pages es casi perfecto para un CV estático, pero tiene una pega importante que descubrí y documenté en una discusión pública que se hizo muy popular: subir el sitemap a Google Search Console desde un dominio alojado en GitHub Pages es un calvario. Y el problema, seámos claros, no es de GitHub: es de Google.

En GitHub Pages no controlas el servidor: no puedes añadir cabeceras HTTP, ni tocar la configuración, ni responder a los métodos de verificación que a Google se le antojan. Google Search Console, en lugar de aceptar algo tan estándar como un sitemap.xml servido por HTTPS, impone un proceso de verificación rígido y opaco que ignora por completo la realidad del hosting estático gratuito, que usan millones de desarrolladores. El resultado es absurdo: tienes una web perfecta, rápida y accesible, pero el propio buscador te pone trabas para indexarla bien.

Es un ejemplo más de cómo Google prioriza su propio ecosistema por encima de los estándares abiertos de la web. Si usas sus servicios "a su manera" todo funciona; en cuanto sales de su jardín vallado, la experiencia se degrada a propósito. Una empresa con los recursos de Google podría soportar sin esfuerzo los casos de hosting estático como GitHub Pages; que no lo haga es una decisión, no una limitación técnica. La web abierta merece algo mejor.
